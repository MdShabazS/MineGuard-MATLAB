## Prioritized findings

### P0 — V2-006 has no demonstrated detection capability on VALIDATION (confirmed scientific result)

`v2/data/V2-006/val_results.csv` has six rows. G07 has four targets: FUSED `TP=0, FP=45, FN=4`; RGB_ONLY `0,19,4`; THERMAL_ONLY `0,9,4`. Target-free G08 has 32, 4 and 1 false events respectively. These values agree with `v2/evidence/V2-006.md` §4. One G07 target has no surface signature by design; the other three visible-signature targets were also missed. No matched event exists from which to estimate target localization error or empirical event uncertainty. The four V2 MATLAB suites passing is a software result only. The V2 TEST groups G09/G10 remain sealed.

**Action:** Keep all user-facing outputs at **SUSPECTED, SIMULATION ONLY**. Do not imply successful mine detection or a fusion advantage. Treat any improvement as a new detector with a new group split and a predeclared evaluation; preserve the original VAL and sealed TEST. Report false alarms per surveyed area and group-level uncertainty in that future study.

### P1 — Main accepts unknown nested public sample metadata (confirmed input-contract defect)

`v2/matlab/+mgv2/+sensors/validateSample.m:11-16` checks exact top-level fields, then validates selected modality values, but does not impose an exact schema on `quality`, `units`, `noise_parameters` or `distortion`. `v2/matlab/+mgv2/+sensors/assertPublic.m:14-27` rejects only listed forbidden names or objects. `mine_location` is absent from `v2/matlab/+mgv2/+sensors/contract.m:32-34`. Therefore a plain nested field such as `s.quality.mine_location = [1 2]` passes those checks; the same pattern applies to `s.units.mine_location` and RGB `s.noise_parameters.mine_location`. The main tests `testV2005Sensors.m:v16` and `testV2006Detection.m:d02` inject names already on the denylist, so they do not cover this case. This is an acceptance gap, **not evidence that a producer emitted hidden truth**.

**Reproduction on main:** obtain a valid RGB sample from `SensorSystem`, add `s.quality.mine_location = [1 2]`, and call `mgv2.sensors.validateSample(s)`. PR #92 records this exact execution, including detector and map acceptance, in `v2/evidence/V2-005-issue-69/README.md` on its own branch.

**Action:** Review PR #92's exact `quality` schema as a targeted fix. Follow it with a separately scoped contract decision for the other nested metadata fields and near-miss names. Preserve producer compatibility and add boundary tests at validator, detector and map.

### P1 — Reported track uncertainty counts the assumed pose term twice (confirmed formula defect)

`v2/matlab/+mgv2/+detect/frameCandidates.m:60` includes `cfg.association.pose_sigma_m^2` in each observation variance. `v2/matlab/+mgv2/+detect/AnomalyDetector.m:223-229` forms inverse-variance weights from those same observation sigmas and then adds `pose_sigma_m^2` again to track variance. For two identical observations with no scatter and observation variance `a + p²`, code reports `sqrt((a+p²)/2 + p²)`, while a single common systematic pose term plus averaged independent part gives `sqrt(a/2 + p²)`. With `a=0` and `p=0.10 m`, those are 0.1225 m and 0.1000 m, a 22.5% difference. `testV2006Detection.m:d13` checks a lower bound, not formula calibration or coverage. The source already acknowledges the double count in `v2/evidence/V2-006.md` §8; calling it merely “slight” understates its effect for short tracks.

The original TRAIN/VAL CSV uncertainty columns are also explicitly **pre-fix** values from an earlier correction (`v2/evidence/V2-006.md` §3). They do not reproduce the current source's uncertainty values. Existing evidence says event decisions do not consume track sigma; this audit did not rerun VAL to independently verify count invariance.

**Action:** Clarify the current report wording and label archived CSVs as outputs of the earlier formula. For a successor detector, separate common pose error from per-frame noise in the variance model, test the arithmetic with hand-computed fixtures, and measure empirical coverage with noisy navigation. Do not silently rewrite frozen CSVs or retune the frozen baseline.

### P1 — Georegistration uses reference geometry while navigation is noisy (confirmed model limitation)

`v2/matlab/+mgv2/+detect/frameCandidates.m:56-60` intersects rays using the sample's `T_world_sensor` and exact public terrain. `v2/evidence/V2-006.md` §8 states that this transform comes from the engine reference pose, while `REPORTED_VIRTUAL` navigation contains bias and noise. Thus the demo's 0.081 m fixture error and public-landmark errors test idealized geometry, not mapping with a field-like navigation solution. PR #93 independently reports, on its separate DEMO diagnostic, median navigation/reference displacement of 1.37 m against an assumed 0.10 m pose term; that measurement is **unmerged research evidence**, not a mainline result.

**Action:** Add a separate pose-input experiment with noisy virtual navigation and landmark residuals, plus a declared operational frame contract. Do not present the current sigma or geometric demo error as real-world geolocation accuracy.

### P2 — RGB residual halo can reject an in-range object (confirmed known limitation)

`v2/matlab/+mgv2/+detect/frameCandidates.m:29-47` computes a 31 px box mean containing the object, takes unsigned residual magnitude and joins neighboring pixels into a component; lines 58-61 size-filter that component. The existing `testV2006Detection.m:d26` and `v2/evidence/V2-006.md` §8 report a 0.90 m synthetic disc measured as 2.03 m and discarded by the 1.6 m gate. This one fixture does not establish the cause of every VAL miss. PR #93 explores alternative residual forms **only in `v2/research/`** and explicitly does not claim event-level improvement.

**Action:** Keep the frozen detector as the comparator. Evaluate halo handling on new, disjoint groups, including clutter, large and low-contrast objects, and record both recall and false alarms before considering a successor.

### P2 — Scientific and acceptance coverage remains incomplete (confirmed gaps)

`v2/evidence/V2-006.md` §5 and §6 explicitly record: no bootstrap interval, no false alarms per hectare, no frame/cell denominators by split, and no auditable TRAIN selection record for frame-level parameters. G07/G08 supply only two VAL groups and four targets. The acceptance matrix in the same evidence file (§6) defers live click interaction and layer toggles to V2-007, shows LiDAR map drawing only partially met, and leaves EVAL-09 TEST unrun. `v2/evidence/V2-002.md` §10 says the early Mac 44-test acceptance session lacked an exact Git SHA; later V2-005/V2-006 evidence provides SHA-pinned Mac runs. These boundaries should remain visible in handover material.

**Action:** Preserve task states and distinguish documentation signoff, software regression, UI integration and scientific acceptance. V2-008/009 should capture the missing denominators and platform provenance without spending the sealed TEST on a detector that failed VAL.
